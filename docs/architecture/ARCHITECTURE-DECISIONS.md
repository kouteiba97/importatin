# Maabar — Architecture Decision Register

**Phase:** pre-build
**Date:** 14 September 2026
**Basis:** `DESIGN-AUDIT.md`, `README.md`, 24 approved artboards, `designs/tokens.css`

Every decision below that is **not** explicitly settled by the approved design is marked
`ARCHITECTURAL DECISION` in the *Origin* column. Decisions the design already settled are
marked `DESIGN` and must not be reopened.

**Status vocabulary:** `DECIDED` · `PROPOSED` · `BLOCKED` · `LEGAL REVIEW`

---

## A · Platform and stack

| ID | Decision | Origin | Reason | Alternatives | Consequence | Status |
|---|---|---|---|---|---|---|
| AD-001 | **Modular monolith**, one deployable backend, module boundaries = bounded contexts | ARCHITECTURAL DECISION | 24 screens, one country, one database, small team. Microservices would add network failure modes and distributed transactions to a system whose hardest requirements — capacity concurrency, audit atomicity, legal invariants — are all *easier* inside one transaction | Microservices; serverless functions | Modules must not import each other's repositories; cross-module calls go through published service interfaces so extraction stays possible | DECIDED |
| AD-002 | **PostgreSQL 16** as the only primary datastore | ARCHITECTURAL DECISION | Needs relational integrity, CHECK/EXCLUDE constraints for legal invariants, FTS + trigram for Arabic search, `bigint` money, row locks for capacity, append-only audit. One engine covers all of it | MySQL (weaker constraint and FTS story); MongoDB (cannot express the invariants) | Extensions required: `pg_trgm`, `unaccent`, `citext`, `pgcrypto`, `btree_gist` | DECIDED |
| AD-003 | **TypeScript end to end**: NestJS API + Next.js web | ARCHITECTURAL DECISION | One language, shared zod contracts and i18n message types across tiers. The NestJS module/guard/pipe model maps directly onto bounded contexts and layered authorization | Django + DRF (better admin scaffolding, two languages); Laravel; Go | Team hires TypeScript only. Guards become the single authorization chokepoint | DECIDED |
| AD-004 | **Next.js (App Router)** for the web tier, public routes server-rendered / ISR | ARCHITECTURAL DECISION | `Landing`, `Marketplace`, `Product Detail`, `Seller Profile` and `Compliance Checker` are explicitly public with no account. A consumer marketplace that search engines cannot index is crippled, and Algerian mobile networks punish large client bundles | Vite SPA (simpler, no SEO, slower first paint); two separate frontends (duplicates components — forbidden by the brief) | Adds a Node rendering tier. Authenticated routes stay client-rendered behind the shell, so one component set serves both | DECIDED |
| AD-005 | **Drizzle ORM + hand-written SQL migrations** | ARCHITECTURAL DECISION | The legal invariants live in CHECK constraints, partial indexes, composite foreign keys and triggers. Drizzle stays close to SQL and does not fight hand-written DDL | Prisma (weak CHECK and partial-index support, migration engine resists raw DDL); TypeORM; raw `pg` | Migrations are reviewed as SQL, which is what a database reviewer wants anyway | DECIDED |
| AD-006 | **No utility CSS framework.** `designs/tokens.css` becomes the CSS variable layer; components use CSS Modules and logical properties | DESIGN | The deck already has one token file consumed by 24 of 24 screens and zero physical `left`/`right`. Tailwind's physical-direction utilities would fight the RTL discipline | Tailwind (with RTL plugin); styled-components | `tokens.css` is copied into the web app unchanged and treated as generated input, not editable by feature work | DECIDED |
| AD-007 | **pg-boss** (Postgres-backed job queue) for async work | ARCHITECTURAL DECISION | Volumes are small; jobs enqueue in the same transaction as the state change that caused them, which removes the "committed but never notified" class of bug entirely | Redis + BullMQ (extra service); RabbitMQ; Kafka (disproportionate at this scale) | Revisit only if sustained job rate exceeds roughly 50/s | DECIDED |
| AD-008 | **Self-hosted MinIO** (S3 API) inside Algeria for private objects; separate public bucket plus CDN for product imagery | DESIGN §9.4 + ARCHITECTURAL DECISION | The design position is "documents stored in Algeria". A foreign object store would contradict it before the ANPDP question is even answered | AWS S3 / Cloudflare R2 (residency fails for KYC); local filesystem (no lifecycle, no signed URLs, no replication) | Ops must run and back up MinIO. Public imagery may sit on a foreign CDN because it contains no personal data | DECIDED |
| AD-009 | **No Redis at MVP.** Sessions, rate-limit counters and caches live in Postgres | ARCHITECTURAL DECISION | One fewer stateful service to run and back up. Session lookup is a single indexed read | Redis from day one | Add Redis when session reads or rate-limit writes measurably contend. Interfaces are written so the store is swappable | DECIDED |

## B · Identity, authentication, authorization

| ID | Decision | Origin | Reason | Alternatives | Consequence | Status |
|---|---|---|---|---|---|---|
| AD-010 | **Opaque server-side sessions in Postgres, not JWT** | ARCHITECTURAL DECISION | Capability and verification state must be revocable *instantly*: an expired general licence has to freeze trip publication immediately, and an admin suspension must bite on the next request. A JWT carries a stale copy of exactly the facts that gate the legal invariants. Session listing and per-device revocation are also stated requirements | JWT access + refresh pair; PASETO | Every authenticated request performs one indexed session read. Accepted: correctness beats a saved round-trip | DECIDED |
| AD-011 | Cookie transport: `__Host-mb_session`, `HttpOnly`, `Secure`, `SameSite=Lax`, path `/` | ARCHITECTURAL DECISION | Cookies cannot be read by injected script; the `__Host-` prefix pins origin; `Lax` permits normal navigation while blocking cross-site POST | Bearer token in `localStorage` (exfiltratable by XSS) | Requires CSRF defence for state-changing requests — see AD-012 | DECIDED |
| AD-012 | CSRF: double-submit token **plus** `Origin` / `Sec-Fetch-Site` check on every unsafe method | ARCHITECTURAL DECISION | Defence in depth; the header check alone fails on old browsers, the token alone fails if a subdomain is compromised | `SameSite=Strict` only | One extra header on mutations, set centrally by the API client | DECIDED |
| AD-013 | **Passwordless identity: phone number + 6-digit OTP.** No password in MVP | DESIGN (`Onboarding`) | The onboarding flow is phone → OTP → profile → capability. There is no password field anywhere in the deck. Not storing passwords removes the entire credential-stuffing and password-reuse surface | Phone + password; email + password | Recovery and SIM-swap become the account-takeover surface and need explicit countermeasures — see `SECURITY-ARCHITECTURE.md` §5 | DECIDED |
| AD-014 | **Roles are capabilities on one identity**, held simultaneously, plus an *active context* the user toggles | DESIGN (`Onboarding` multi-select; `Importer Home` / `Trader Home` `['import','buy']` switcher) | The deck shows one account holding importer and trader at once and toggling "أنا أستورد / أنا أشتري" | Separate accounts per role; a single `role` enum column | Authorization never reads a `role` column. It evaluates *(capability, verification level, resource ownership)* | DECIDED |
| AD-015 | Authorization is a **policy layer evaluated server-side on every request**, in five ordered gates: authenticated → capability held → verification level → resource ownership/visibility → action-specific precondition | ARCHITECTURAL DECISION | The brief requires multi-level authorization and IDOR/BOLA prevention. Ordered gates make every denial explainable and testable | Scattered `if` checks in controllers; an off-the-shelf RBAC library | Every endpoint declares its policy in metadata; a test asserts that no route is missing one | DECIDED |
| AD-016 | Verification **levels are derived, never assigned**: `L0..L3` is computed from the set of currently-valid verified documents plus countable record facts | DESIGN (`Verification` ladder) | The ladder screen shows level as a function of documents, each with its own expiry. A stored level would drift out of sync the moment a licence lapses | Stored `level` column updated by a job | Level is a derived value recomputed on document state change and on a daily expiry sweep | DECIDED |

## C · Legal invariants in the schema

| ID | Decision | Origin | Reason | Alternatives | Consequence | Status |
|---|---|---|---|---|---|---|
| AD-017 | **A consumer-facing listing is structurally impossible for a non-eligible seller**, enforced by a composite foreign key to `trader_profiles(user_id, listing_eligible)` where `listing_eligible` is a generated column requiring a verified commercial register | DESIGN §13.1 ("enforce at schema level") | The brief demands schema-level enforcement, not a service check. A composite FK makes the illegal row unrepresentable — no application bug, migration script or admin console can create it | Application-layer guard only; trigger; CHECK against a subquery (not possible in Postgres) | Revoking eligibility while listings exist raises a FK violation; the domain service must archive listings first, which is the desired explicit, audited behaviour | DECIDED |
| AD-018 | **Maabar never records a goods payment.** No amount column in any table may represent money moving through Maabar for goods. Subscription billing lives in a separate schema (`billing.*`) with no foreign key to any commercial entity | DESIGN §13.2 | The separation must be visible in the data model, not only in policy prose. A missing foreign key is a stronger guarantee than a code review | One `payments` table with a `kind` discriminator | A report joining subscriptions to commitments is impossible to write by accident | DECIDED |
| AD-019 | **Deposit declaration ships disabled**: tables and endpoints exist, gated by `features.deposit_declaration` (default `false`); the commitment state machine treats `secured` as an optional stage and permits `accepted → buying` directly | DESIGN §9.2 + the `Commitment` artboard (`accepted` copy: "the next step is to agree a deposit *if you both want*"; `dep:false` on `accepted`) | The hold must be a flag, not a rewrite. The artboard already models `secured` as skippable | Omit the tables entirely (rewrite later); ship enabled (legal risk) | A lawyer's "no" becomes a config change plus a data-deletion job. A "yes" is a flag flip | LEGAL REVIEW |
| AD-020 | **No composite trust score anywhere.** Published metrics are `completion_rate`, `median_response_time`, `price_stability_rate` and `confirmed_transactions`, each backed by a stored breakdown of its raw inputs | DESIGN (`Importer Profile` `SHEETS`) | The profile screen opens each figure into its exact numerator, denominator and exclusions. That is the specification, not an illustration | Weighted score; star rating | Each metric is a materialized row carrying its inputs; the API returns figure and breakdown together | DECIDED |
| AD-021 | **Trip *value* capacity is private to the importer**; only weight and volume are exposed to counterparties | DESIGN (`Discover` source comment: "the value meter is the importer's legal cap against their own money — never shown to a counterparty") | This is a field-level visibility rule, not a UI choice. It leaks how much cash the importer is carrying abroad | Expose all three; expose value as a percentage | Trip serializers are role-aware: `TripOwnerView` vs `TripPublicView`, enforced in the query layer, never by omitting a field in the client | DECIDED |
| AD-022 | **Regulatory values are versioned rows with effective dates**, read at render; historical records resolve against the version effective at their own timestamp | DESIGN §10, §13.4 | `Trip Creation` displays the cap *with its effective date*, and the audit requires historical interpretability | Constants; environment variables; a single-row settings table | Every rule read takes an `as_of` timestamp. Commitments store the `rule_version_id` they were created under | DECIDED |
| AD-023 | **Reviews are append-only with one right of reply**; never hard-deleted, hidden only by an audited moderation decision that remains visible as "removed by moderation" | DESIGN §13.5 | Deletion would destroy the only trust substrate the product has | Soft-delete hidden silently; allow author deletion | `reviews` carries no `DELETE` grant for the application role | DECIDED |
| AD-024 | **Admin corrections are new decisions referencing the prior decision** (`supersedes_decision_id`), never updates | DESIGN §13.6 | Required for auditability, and the only way to answer "what did we decide, and when did we change our mind" | Mutable decision rows with an audit trigger | `admin_decisions` carries no `UPDATE` or `DELETE` grant | DECIDED |

## D · Domain modelling

| ID | Decision | Origin | Reason | Alternatives | Consequence | Status |
|---|---|---|---|---|---|---|
| AD-025 | **No generic `Order` entity.** `ProductListing`, `SourcingRequest`, `SourcingOffer`, `Trip` and `Commitment` stay distinct | DESIGN + the artboards | They have different actors, lifecycles, visibility rules and legal meanings. Collapsing them would force one state machine to serve five, and would make Maabar look like a party to the sale | One polymorphic `Order` | Five smaller machines, each fully testable — see `DOMAIN-MODEL.md` §3 | DECIDED |
| AD-026 | Commitment lifecycle uses the **artboard's vocabulary**: `proposed · accepted · secured · buying · transit · handover · done`, plus `disputed · cancelled · expired` | DESIGN (`Commitment.FLOW`, `Commitment.SWITCH`) | The brief's illustrative list (`Interested / Requested / Committed / In Progress / Completed`) does not match the approved design. The design wins under the stated source-of-truth hierarchy | The brief's list | Reported as a discrepancy, not silently substituted — see `STATE-MACHINES.md` §1.1 | DECIDED |
| AD-027 | **A conversation is attached to exactly one context object** (listing, sourcing request, trip, commitment or dispute), and structured **action cards** are first-class message kinds | DESIGN (`Messages` `kind:'agree'`, `kind:'handover'`) | The deck shows agreement proposal and handover confirmation happening *inside* the thread, with CTAs that mutate domain state | Free chat plus separate action screens | A message may carry a domain action; the action's effect is transactional with the message insert | DECIDED |
| AD-028 | **Aggregated demand is a materialized projection**, refreshed on a schedule, exposing counts and price bands only — never counterparty identities | DESIGN (`Demand Board`: "مبنيّة على 214 طلباً", counts, bands and wilaya names, no names) contrasted with `Trip` (named confirmed buyers) | The two surfaces deliberately show different privacy levels | Compute live from `sourcing_requests` on every load; expose identities | A `demand_aggregates` table keyed by (category, wilaya, period) with a minimum-cell-size rule to prevent re-identification | DECIDED |
| AD-029 | **Handover requires dual confirmation** and carries a 6-digit code | DESIGN (`Messages` handover card, `رمز التأكيد 4 7 2 9 1 6`; audit §5 "Both sides must confirm") | Prevents unilateral completion, which would corrupt the completion-rate metric | Single-party confirmation; QR code | Code is server-generated, single-use, scoped to the commitment and rate-limited. Direction of presentation is specified in `STATE-MACHINES.md` §2.6 as an ARCHITECTURAL DECISION | DECIDED |
| AD-030 | **Human-readable reference IDs** (`CMT-26-0331`, `VER-26-0881`, `ADM-002`) are a second identifier alongside the UUID primary key | DESIGN (visible in the `Commitment` header and `Admin Console` rows) | They are operational and legal handles that users read aloud and admins search by | UUIDs only; sequential integers as primary key | A `reference` column, unique, generated as `PREFIX-YY-NNNN` from a per-type yearly sequence | DECIDED |
| AD-031 | Money stored as **`bigint` centimes**; weight as **integer grams**; volume as **integer cubic centimetres** | ARCHITECTURAL DECISION (the brief forbids floats) | Exact arithmetic, no rounding drift, no locale parsing ambiguity. `1 800 000 DZD` = `180000000` centimes, far inside `bigint` | `numeric(14,2)` (exact but slower and invites float casts in JS); float (forbidden) | All formatting happens in one place and only at the edge. A JS `number` holds these values safely below 2^53 | DECIDED |
| AD-032 | **Prices are bands, not points**, wherever two parties agree in advance: `(min, max)` or `(target, tolerance_pct)`, with a validity date | DESIGN (`Commitment.TERMS` "نطاق السعر 4 800 – 5 200"; `Sourcing Request` "2 100 دج ± 8%", "صلاحية النطاق حتى 14 أكتوبر") | Maabar records an indicative range agreed between users; it never records a settled transaction price, because it is not party to the sale. This is also exactly what `price_stability_rate` measures against | Single agreed price (implies a sale Maabar witnessed) | A consumer `ProductListing` keeps a single displayed price — that is the trader's own shop price, a different thing | DECIDED |

## E · Cross-cutting

| ID | Decision | Origin | Reason | Alternatives | Consequence | Status |
|---|---|---|---|---|---|---|
| AD-033 | **Postgres FTS + `pg_trgm` for search**, with an Arabic normalization function. No Elasticsearch at MVP | ARCHITECTURAL DECISION (the brief explicitly invites this answer) | The corpus is roughly 1.2k listings, tens of profiles and single-digit trips. A dedicated search cluster would be the largest operational burden in the system, serving a table that fits in memory | OpenSearch / Elasticsearch; Meilisearch; Typesense | Revisit above roughly 100k listings, or when ranking needs learned signals. The interface is a `SearchPort` so the engine is swappable | DECIDED |
| AD-034 | **Arabic normalization is explicit and shared** between indexing and querying: strip tatweel and diacritics, fold alef and hamza variants, fold taa marbuta to haa, fold Arabic-Indic digits to Western | ARCHITECTURAL DECISION | Postgres ships no Arabic stemmer. Without folding, "معطف", "معاطف" and "المعطف" miss each other, and users type all three | Rely on the `simple` configuration alone; ship a stemmer extension | One immutable SQL function used both in the generated `tsvector` column and in query preparation. Changing it requires a reindex migration | DECIDED |
| AD-035 | **Numbers are LTR-isolated at the formatter**, never by callers | DESIGN §13.7 and every artboard's `ltr()` / `fmt()` helper | The deck already implements exactly this: 14 formatters wrapping output in `U+2066…U+2069`. Leaving it to callers guarantees a missed case | Wrap in markup with `<bdi>` only; rely on paragraph direction | A single `format` module in shared code, used by both tiers. A lint rule forbids raw `toLocaleString` in components | DECIDED |
| AD-036 | Messaging realtime: **poll while a thread is focused, Web Push when it is not.** No WebSocket server at MVP | ARCHITECTURAL DECISION (the brief asks for the simplest architecture that supports the UX) | The UX is a two-party negotiation thread, not a live group chat. Polling survives Algerian mobile-network churn better than a socket that dies silently | WebSocket; SSE; long-poll | One `GET /conversations/:id/messages?after=` endpoint serves both polling and initial load | DECIDED |
| AD-037 | **Audit log is append-only with a per-stream hash chain**, monthly partitions, and no `UPDATE` or `DELETE` grant to the application role | ARCHITECTURAL DECISION (the brief asks for an immutability strategy) | Tamper *evidence* is achievable without a ledger database: each row stores `prev_hash` plus a hash over its own canonical content | Trigger-blocked table only; external append-only store; blockchain (no) | A nightly verifier walks each stream and alerts on a break. Immutability against a database administrator still requires off-box shipping — see `SECURITY-ARCHITECTURE.md` §11 | DECIDED |
| AD-038 | **PWA at MVP is installability, shell caching and resumable uploads only.** Offline browsing of cached results is V1; background sync is Future | DESIGN §7 (offline states are drawn for the `Search` cached-results banner and `Verification` resumable upload) plus ARCHITECTURAL DECISION on scope | Exactly two offline states are drawn. Building a general offline data layer for a marketplace whose data goes stale in hours is unjustified | Full offline-first with a local mutation queue | The service worker caches app shell, tokens, fonts and the last search result set. Uploads use chunked resumable transfer | DECIDED |
| AD-039 | **Subscription payment has two paths**: manual CCP / BaridiMob receipt into an admin confirmation queue, and CIB / Eddahabia card through the SATIM gateway with instant activation | DESIGN (`Records` `METHODS`; `Admin Console` billing queue "تحويلات CCP بانتظار التأكيد") | Both are drawn. The manual path is not a stopgap — it is how much of the Algerian market pays | Card only; manual only | Billing needs a receipt-upload flow, an admin queue, and one idempotent activation path shared by both | DECIDED |
| AD-040 | **The web tier is a thin BFF.** No domain rule, no authorization decision and no regulatory value is implemented in Next.js | ARCHITECTURAL DECISION | Two enforcement points drift. The server-rendered tier holds a session cookie and calls the same API a browser would | Duplicate checks in the BFF for speed; Next.js as the whole backend | A server-rendered page that shows data the API would refuse is a bug, caught by the authorization test suite | DECIDED |
